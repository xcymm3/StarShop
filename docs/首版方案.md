# StarShop 首版方案

状态：开发基线 v0.1，2026-11-13。

## 目标与边界

玩家扮演空间站店长，收购拾荒客和商人带来的物品，再卖给船员、旅客与收藏家。单次操作以查看、判断和点击成交为主，竖屏、单手操作。一次交易即可退出，不要求完成一天。

本方案以本次讨论中用户明确保留的机制为准。未确定的数值和交互在下文标为“首版默认值”，用于可玩的本地原型，后续可调整。不得把建议的“接待五位算一天”替换用户确定的“成交五笔算一天”。

首版实现于 Taro + React + TypeScript，先支持 H5 调试，同时保持微信小程序构建通过。经营规则不依赖 DOM 或 Taro；平台存储独立封装。

## 保留的核心内容

- 收购与出售：拾荒客来卖货，星际旅客来买货。
- 商品差异：类别、品质、状态和参考价，卡片突出最多三个信息点。
- 顾客差异：拾荒者、船员、商人、收藏家，有各自预算、偏好和短对白。
- 有限资金与仓位，收购需要同时满足两项条件。
- 店铺成长：扩仓、增加展示位、等级解锁品类。
- 空间站氛围：原创顾客对白、商品来历、每日空间站消息。
- 简单鉴定：一次查看揭示品质和更准确的估价，不做多工具操作。
- 今日热销类别：只随游戏日变化，不按现实时间刷新。
- 固定升级位，无自由摆放和复杂拖拽。
- 每完成五笔买入或卖出交易推进一个游戏日。
- 每七个游戏日收租，其他生存压力移除。
- 没有离线收益，也没有离线惩罚。

不纳入首版：战斗、探索、养殖和遗传、生产链、多人、广告、充值、云存档、登录、贷款、腐坏、复杂势力剧情、自由家具布置、长轮议价。

## 经营流程

接客 → 查看来货或求购需求 → 可选鉴定／挑选货物 → 接受或拒绝 → 反馈结果 → 下一位。

首版默认采用固定报价，暂不议价。拒绝不扣钱、不消耗仓位、不推进日期。买入和卖出成功均计一笔。清仓、鉴定和升级不计成交进度，不推进日期。跨天不阻断接客，使用提示展示热销变化与收租结果。

每位顾客的身份、商品、预算和报价生成后立即保存，不因刷新、切后台或重新打开而改变。只有明确接待下一位时才生成新顾客。

## 数值基线（首版默认值）

| 项目 | 默认值 |
|---|---|
| 初始资金 | 650 星币 |
| 初始库存 | 3 件已鉴定商品 |
| 初始仓位 | 8 件，每件占 1 格，不做旋转或堆叠 |
| 初始展示位 | 2 个，商品仍占仓位 |
| 商品种类 | 24 种，分机械、补给、遗物、数据四类 |
| 品质 | 普通、精良、稀有 |
| 状态 | 损坏、磨损、完好 |
| 鉴定 | 收购前支付 8 星币，每件只需一次，不改变既有报价 |
| 一天 | 五笔成交，买入和卖出都计数 |
| 租金 | 每周 120 星币，在第 7、14、21…日结束时收取 |
| 扩仓 | 每次增加 4 格，价格递增 |
| 增加展示位 | 每次增加 1 位，价格递增 |
| 店铺等级 | 累计成交 15／40 笔达到 2／3 级，解锁额外商品 |

品质和状态作用于参考价值。买家报价还受偏好、当日热销、等级与预算影响。参考价不是保底成交价。所有价格为整数，使用统一规则计算，拒绝负价、无物品成交或重复成交。

热销加价默认 20%，等级销售加价每级 3%。展示商品更容易被买家选中，首版不再叠加固定展示加价。

## 周租与经营恢复

时间只由成交推进；退出多久都不额外扣租。交租会先扣除可用资金，不足部分成为欠租，资金最低为 0。欠租不结束存档、不封店，玩家可在账本主动补缴。

库存始终可按参考价值的 45%清仓回款。清仓不算一笔成交，避免刷时间。空库存时生成可收购来货；有库存时维持买家出现机会。资金不足时可拒绝并换客，不强制收货。初始三件库存提供第一轮周转空间。

本版没有永久破产判定。需要通过测试检查零资金、满仓、欠租和无匹配买家的恢复路径。

## 信息与存档

存档内容：版本、资金、库存、展示列表、当前顾客及报价、游戏日、当日成交进度、总成交数、升级等级、欠租、交易流水、随机生成器状态。

每次接客、鉴定、成交、拒绝、展示变更、升级、补租后先持久化，再更新界面。写入失败时阻止该操作并给出错误，不显示虚假的“已保存”。重启恢复当前状态；不根据现实时间计算收益或惩罚。

首版使用本地存档。存档包含版本和结构校验，损坏时保留原数据并提示恢复新局，不静默覆盖。重开需二次确认，先保存旧档备份。暂无跨设备同步。

## 必要界面与状态

尽量合并为四个主入口，其他通过详情层展示，避免手机端长流程。

| 编号 | 界面／状态 | 主要内容与操作 | 优先级 |
|---|---|---|---|
| 01 | 店铺柜台 | 资金、日期、成交进度、当日热销、当前顾客 | P0 |

| 05 | 出售报价 | 选中商品、参考价和成交价、出售确认 | P0 |
| 06 | 交易完成 | 资金变化、进度、接待下一位 | P0 |
| 07 | 仓库 | 容量、分类、展示标记、库存列表 | P0 |
| 08 | 库存详情 | 属性、来历、入手价、展示／撤下、清仓确认 | P0 |
| 09 | 店铺升级 | 等级、扩仓、展示位、花费和效果 | P0 |
| 10 | 账本 | 周租、欠租补缴、累计经营、最近流水 | P0 |

界面风格由本次原游戏多状态截图的视觉观察确定，不自行提前指定风格。不把原游戏横屏多窗口直接缩小到手机，不复制商业游戏的画面、音乐、角色或商品图。

## 视觉参考的取得与使用

用户于本次对话明确允许恢复此前“后台启动图形 Player + Unity 自身截图”的办法，仅用于参考图采集；电脑控制仍禁止。

准确称谓：这是带渲染的后台进程，不是 NullGfxDevice 无图形模式。后者不能产出正常渲染截图。本次不需要也不启动 Unity Editor。

目标：超过十张不同界面状态的真实原游戏截图，记录状态、调用入口、文件路径和局限，保存在原逆向工作区，默认不推送到 StarShop 仓库。无法到达的界面诚实列为未取得，不使用重复画面或新项目截图充当原作截图。

观察重点：店铺与柜台的主次关系、商品信息层级、交易确认、库存、账本、升级或相关操作面板。角色选择和设置画面可作辅助参考，不能替代经营参考。

## 验收条件

1. 从新局完成收购、鉴定、出售、清仓、展示、升级和周租流程。
2. 买卖五笔跨日；鉴定、清仓、升级和拒绝不跨日。
3. 第七日最后一笔成交触发一周租金，重复操作不重复收租。
4. 缺钱、满仓、物品已售、重复点击不会产生负资金或复制物品。
5. 刷新恢复当前报价、库存、日期和随机状态，不产生离线变化。
6. 存储失败时交易不生效；坏档有明确恢复入口。
7. 320、375、414、768 宽度无横向溢出，主要按钮不需悬停操作。
8. 规则单元测试、TypeScript 检查、H5 和微信小程序构建通过。
9. 使用真正 headless 浏览器验证新项目流程；不使用桌面自动化。
10. 原游戏参考截图和新项目验证截图分别标注，不混淆来源。
